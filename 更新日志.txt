[v3.2]  2026-10-26   文件库 / 预览 / 变动通知 / 归档 + 断点续传 / 并发 / 打包 + 待办 / 置顶 + 消息懒加载
· 一、文件相关（新增「文件」视图）
    - 之前共享文件夹只能靠聊天记录看，别人从资源管理器放进去的东西在程序里
      完全看不见。现在聊天区顶部多了  聊天 | 文件 | 待办  三个视图。
    - 文件页列出共享文件夹根目录和子目录：文件夹排前、文件按修改时间倒序、
      顶部显示当前路径和总大小；进子目录有「↑ 上一级」；搜索框自动变成
      「搜索文件名」。_lanchat 目录和没传完的 *.part 不显示。
    - 每行右侧四个操作：预览 / 打开 / 定位 / 删除。删除删的是真文件，
      两台都没了，所以先弹确认。单击一行 = 能预览就预览，否则用默认程序打开。
    - 新增接口：GET /api/files（列目录）、/api/open（默认程序打开）、
      /api/preview（预览）、/api/archive（归档建议 / 执行）、/api/zip（打包）。
· 二、在线预览
    - 文本 / 代码 / CSV / JSON / 日志走 text/plain; charset=utf-8；
      图片、音视频、PDF 用 http.ServeContent 支持拖动进度条，
      并且回 Content-Disposition: inline（不然 WebView2 会把 PDF 当附件下载）。
    - 中文 GBK 编码的 txt 自动识别：先用 windows.MultiByteToWideChar
      （代码页 0 = CP_ACP，也就是系统默认 ANSI）转 UTF-16。
      判断是否 UTF-8 只校验前 4KB —— 整文件校验会因为截断点正好切在汉字
      中间而误判成 GBK，导致好好一个 UTF-8 文件变乱码。
    - 文本超过 2 MB 只发前 2 MB，靠 X-Truncated 响应头告诉页面，页面顶部
      提示「只显示前 2 MB，要看全用打开」。
    - 其他类型（docx / xlsx / zip…）返回 415，页面提示改用默认程序打开。
    - 预览浮层 #pv 从 top:42px 开始，不遮标题栏的拖拽区和关闭按钮。
· 三、共享文件夹变更通知
    - 没用 ReadDirectoryChangesW，采用「定期快照 + 比对」：2.5 秒扫一次
      根目录（只一层），签名是 名字+大小+修改时间，变化的进一个 200 条
      的环形事件队列，seq 自增。SMB 网络共享上变动通知经常静默失效，
      快照法稳、代码量也小一个数量级。
    - 新接口 GET /api/watch?after=<seq>，页面每 2 秒拉一次，收到别人放进来
      的文件就在聊天里插一条系统提示，点它跳到文件页。
    - 自己写文件时不报（否则发完文件自己先收到一条）：handleWrite /
      handleMkdir 里调 watcher.noteSelf(名字)，30 秒内同名的变化算自己干的。
    - 系统提示只在本地显示、不写聊天记录，两台各写一条就重了；
      页面侧还按 seq 去重（一次轮询可能重复消费同一批事件）。
    - 共享断开时把快照清空并置 seeded=false，恢复后重建基线，
      免得把老文件全当成新文件报一遍。
· 四、根目录归档建议
    - 根目录散着 ≥20 个文件时，文件页顶部出现「把 2026-10 的 N 个归到
      「2026-10」目录？」。GET /api/archive 只算建议，POST 才真搬（os.Rename）。
    - 只碰根目录的散文件：目录、_lanchat、*.part 一律跳过；被别的程序占用的
      跳过并在结果里报数量。
· 五、传输相关
    - 断点续传：新增 GET /api/stat 拿目标文件已有大小；前端 createWritable
      增加 keep 选项（不截断，第一次也走 append），从 .part 已有字节往后续写，
      传完再 /api/rename 成正式名。测试里 5 MB 文件带了 2 MB 的 .part，
      最终正好 5242880 字节（不是 7 MB），说明确实是续写不是重传。
    - 文件夹并发复制：sendFolder 拆成 sendFolder（判断要不要问打包）+ 
      doSendFolder（4 路 worker 从队列里抢文件），原来是 for 循环 await 串行。
    - 打包发送：拖进来的文件夹 ≥30 个文件时先问一句，选「打包发送」就在
      页面里压成 zip 再上传。为什么在页面里压：从 <input>/拖拽拿到的只有
      File 对象，没有绝对路径，Go 那边读不到原始文件。
      因此手写 zip：local header 30 字节 + central directory 46 字节 +
      EOCD 22 字节，CompressionStream('deflate-raw') 压缩（不支持就 store），
      CRC32 查表，文件名打上 UTF-8 标志位 0x0800。只用标准 Web API，
      不引任何第三方库。文件页对文件夹点「打包」走后端 /api/zip。
    - 用 self-drawn 的 #askbar 轻确认条替代 window.confirm ——
      WebView2 里 window.confirm 的行为不稳（有时直接返回 true）。
· 六、协作相关（不做共享剪贴板、不做导出会话）
    - 待办清单：共享文件夹\_lanchat\todo.json，结构
      {v, items:[{id,text,done,by,ts,doneBy,doneTs}]}；接口
      GET/POST /api/todo，POST 的 op 有 add / toggle / del / clearDone。
      勾完记下「谁完成的、什么时候」，标签上的数字是未完成条数。
    - 置顶公告：\_lanchat\pin.md，GET/POST /api/pin，text 为空就删文件。
      顶部黄条显示；点 × 只在本机收起（存 localStorage）。留空保存 = 清空。
    - 两个文件都走 writeAtomic（先写 .tmp 再 rename）+ 进程内 mutex，
      两个人在同一秒改也不会读到半个文件。跨机器仍是最后写入者赢，
      日常够用。
· 七、消息存储优化（启动快了很多）
    - 老实现：启动时列一遍 msgs 目录，再对每条消息发一次 /api/read。
      几百条还行，几千条就要几十秒。
    - 现在后端批量读：GET /api/msgs?path=&before=&after=&limit=，
      一页默认 300、上限 800，返回 [{fn, m}]。文件名是
      「13 位时间戳-6 位随机.json」，字典序就是时间序，排序和筛选全在
      文件名上做，不读文件内容、不 stat。
    - 前端懒加载：启动只取最近 400 条，MSG_WATER 记最新 ts 做增量水位；
      列表滚到离顶 60px 以内触发 loadEarlier()，取 before=<最早 ts>&limit=200，
      取完用 scrollTop += scrollHeight - h0 把视口钉在原地（不然会跳）。
    - tick() 里对 watch 的轮询也统一到这一处，避免各处定时器打架。
· 八、整体代码审查（简洁性 / 必要性 / 占用）
    - 新增功能按职责拆成独立文件：msgs.go（批量读消息 + stat）、watch.go
      （目录快照）、library.go（文件列表 / 预览 / 归档 / 打包 / 打开）、
      collab.go（待办 + 置顶）。main.go 只留路由和启动逻辑，不再继续膨胀。
    - 删掉确认为死代码的四处：
        · Go：pendingPayload()（真正的实现是 takePendingMsg，这个是老版本残留）
        · Go：removeShare() 和 pNetShareDel（从来没删过共享，冲突只会加后缀）
        · Go：isPreviewable()（预览分支直接按扩展名查表，用不到它）
        · JS：WINMODE / applyWinMode / setWinMode（v2.8 删主页后就已经没有
          「切换形态」这回事，只剩一个恒等于 'chat' 的空壳和三次无用调用。
          改成启动时给 body 加一个 mode-chat 类，行为不变，少了 9 行）
        · Go：/api/window 的 "mode" 动作和 setWindowMode()（同一件事的后端一半）
        · CSS：.wsep、.nsmsg.warn（都是旧标题栏 / 旧提示样式，已无人使用）
    - 修一个真 bug（顺手查出来的）：文件页的搜索原来「慢一个按键」。
      渲染挂在 input 监听里、关键词在另一个监听里更新，两者顺序固定，
      所以第一下渲染永远用的是上一次的关键词。现在把「文件页 / 待办页
      重新渲染」统一收进 applyFilter()，同一个按键只渲染一次，关键词一定是新的。
      文件页可能上千行，连续打字时攒 90ms 再渲染，不会一顿一顿。
    - 修一个潜在卡顿：目录扫描（watch.scan）原来全程持锁做 os.ReadDir。
      共享盘掉线时 ReadDir 会卡十几秒，而发消息要调 noteSelf（同一把锁），
      结果就是「网盘一断，界面跟着僵住」。现在 ReadDir 放到锁外，
      只把「比对 + 入队」这一小段放进锁里，并加了「扫到一半换了文件夹就作废」
      的检查。
    - 预览的编码判断从「整体 utf8.Valid 最多扫 3 遍」改成只看末尾几个字节
      （utf8.DecodeLastRune），2MB 文本的预览少扫 6MB 内存。
    - /api/zip 增加空 root 校验（还没打开共享文件夹时返回 400 而不是 500）。
    - 函数查重：后端 100+ 个函数、前端 200 个函数都没有重名；
      所有文件操作仍然统一过 cleanPath（远程路径另外走 resolveOpenPath）。
    - 体积 6.78 MB（v3.1 是 6.3 MB，多出来的是新功能），
      常驻内存与 v3.1 基本持平；消息轮询从「列目录 + 每 400ms 全量比对」
      变成「一次批量接口 + 400ms 增量」，几千条记录时启动从几十秒降到 1 秒内。

[v3.1]  2026-10-26   身份不再丢失 + AI 消息适配 + @ 提及
· 一、修「每次重启昵称被重置」和「自己发的消息跑到左边」（同一个病根）
    - 根因：昵称和 peerId 原来只存在页面的 localStorage 里，而 exe 每次启动
      监听的端口都是随机的（127.0.0.1:0），端口一变页面的 origin 就变了，
      localStorage 相当于换了一个空抽屉 —— 于是昵称回到「电脑-XXXX」，
      peerId 也重新生成。老消息记的是旧 peerId，自然对不上，就被当成
      别人发的排到左边去了。
    - 现在身份存在配置文件 %APPDATA%\LanChat\config.json 的 profile 里：
        "profile": { "name": "小明", "peerId": "4248dc32…" }
      peerId 首次启动生成一次，之后固定不变；昵称改了就写进去。
      重启不丢，换共享文件夹也跟着走（这就是「一台电脑的昵称在所有文件夹里
      是同一个」）。
    - 新增接口 /api/profile（POST {name}），/api/info 多返回 peerId 和 nick。
· 二、判定「自己发的」改成双保险
    - 以前只比 peerId。升级前那些老消息的 peerId 已经找不回来了，
      于是加了设备名兜底：m.dev 等于本机计算机名的，也算自己发的。
    - 效果：升级后打开历史记录，以前错跑到左边的自己消息会自动回到右边。
· 三、AI 消息适配
    - bot:true 的消息：头像换成紫色机器人图标、昵称后面加一个「AI」标签，
      一眼能看出不是人。
    - 打字机效果：机器人回复带 pending:true 时，前端每轮重读这个文件，
      内容一变就原地刷新气泡，末尾还有一根闪烁的光标 —— 配上
      LanchatBot v1.1 就是逐字冒出来。收尾后 pending 去掉，光标消失。
· 四、@ 提及
    - 输入框里打 @ 自动弹出候选（当前在线的其他设备，AI 机器人自动在列，
      并且排在第一个）。支持上下键选、回车或 Tab 确认、Esc 关掉，
      继续打字会按名字过滤；没人在线时给一句明确的提示。
    - 消息右键菜单多了「＠ 提到 XXX」（对方的消息才有，自己的没有），
      点一下把「@名字 」塞进输入框。
    - 配合机器人 v1.1：触发词按最长匹配，「@AI 助手」会被整体吃掉，
      不会把「助手」两个字留在问题里。
· 五、顺带
    - 页面暴露 __LANCHAT_API.me() / isMine() / atTargets() 等，给自动化测试用
    - 自检项增加 mineByDev / botStyled / atMention / ctxMention / meId

[v3.0]  2026-10-25   三个按钮统一 + 「文件夹内打开」修好远程 + 文件/文件夹直落共享文件夹
· 一、每个气泡都是三个按钮（自己和对方的都一样）
    - 以前：本机的气泡只有「复制 + 打开文件夹」，对方的气泡只有「复制 + 另存为」，
      想另存自己发的文件、想定位对方发的文件，都没地方点
    - 现在统一成三个（buildActions 不再看 mine / other 分支）：
        · 复制     文字→复制文字；图片→复制图片（PNG 进剪贴板）；
                   文件/文件夹→把**本体**放进 Windows 剪贴板（CF_HDROP）
                   —— 可以直接粘到资源管理器、微信、Word 里，不再是「复制文件名」
        · 文件夹内打开  在资源管理器里选中这个文件 / 打开这个文件夹
        · 另存为…      弹系统「选择文件夹」对话框，整份复制过去；文字消息存成 .txt
    - 文件卡片的那个小按钮也跟着变：v3.0 的文件/文件夹显示「打开」（直接弹资源管理器），
      老消息（还在 _lanchat\blobs 里的）仍然显示「保存」

· 二、修 bug：「文件夹内打开」在共享文件夹不在本机时打不开
    - 原因有两个，都跟「路径形态」有关：
        ① 共享文件夹在对方电脑上时，本机这一侧往往是一块映射网络盘（Z:）。
           映射盘只在「当前登录会话」里存在 —— 程序一旦以管理员身份跑，
           或者换了用户，Z: 在这个进程里根本看不见，explorer 自然也打不开
        ② 后端 handleReveal 原来用 cleanPath（必须落在共享根内）校验，路径是
           网络盘/共享地址时经常被判成「路径不在共享文件夹内」，直接 400
    - 修法：
        · 新增 files_win.go，里面有 dirAddress()：把当前共享根统一算成共享地址
            - 本来就是 \\主机\共享名  → 原样
            - 是一块映射盘（Z:）      → WNetGetUniversalNameW 查它映射到哪，换回共享地址
            - 是本机磁盘              → coverShare() 找覆盖它的共享，拼成 \\主机\共享名\子目录
          /api/where 把它和 root、kind（unc/map/local）一起返回给页面
        · 页面在 enterRoom 时取一次（S.where），之后：
            - 气泡里的地址显示用它（两台电脑看到的是同一个地址）
            - kind 是 map/unc（也就是共享文件夹不在本机）时，「文件夹内打开」「复制」
              「另存为」都改走共享地址，不再依赖本机盘符
        · handleReveal 不再套 cleanPath，改成 resolveOpenPath()：
            先看本机路径在不在 → 不在就把映射盘换成共享地址再试 → 反方向（共享地址
            换成本机盘符）也试一次 → 都不行才报「打不开这个位置：… 现在访问不了
            （网络盘可能没连上）」，不再默默把资源管理器开到一个莫名其妙的地方
        · 打开失败时先试 explorer.exe，再兜底 ShellExecuteW；文件才用 /select，
          文件夹直接打开目录本身（原来没区分）
        · 侧边栏的「在文件管理器中打开」也走同一套解析

· 三、文件 / 文件夹：直接复制进共享文件夹，消息显示地址
    - 以前：不管什么文件都塞进 _lanchat\blobs，文件名变成「时间戳-id__原名」，
      资源管理器里根本看不出是什么；发文件夹则直接发不出去（拖进来只会得到一个 0 字节的坏文件）
    - 现在：
        · 普通文件 → 共享文件夹根目录，**用原来的名字**；重名自动「名字 (2)」
          传输时先写「名字.part」，传完再 /api/rename 改成正式名字
          （中途断了不会留下一个「看起来完整」的坏文件，也不会出现半截消息）
        · 文件夹 → 整个目录树照抄进共享文件夹（子目录、文件都在），重名同样加 (2)
          拖进来的文件夹用 webkitGetAsEntry 递归读，不用先拿到真实路径
          新增工具条按钮「发送文件夹」（<input webkitdirectory>），按
          webkitRelativePath 还原目录树
        · 消息格式新增 {type:'folder', name, path, files, size}，
          「文件」消息多了一个 path（相对共享根的位置）；两种都显示：
            名字 / N 个文件 · 大小 · 在共享文件夹里 / \\主机\共享名\名字
        · 图片还是走 _lanchat\blobs（气泡里要直接预览，粘贴进来的截图也没名字）
    - 新接口：
        /api/where           当前共享根的本机路径 + 共享地址 + 类型
        /api/unique          {parent,name,dir} → 不重名的名字
        /api/rename          {from,to}   .part → 正式名
        /api/copy            {src,dstDir,name?} → 文件/文件夹整份复制（递归、重名自动改）
        /api/save-text       {dir,name,text} → 文字消息另存成 .txt
        /api/clipboard-file  {path} → CF_HDROP，把文件本体放进剪贴板
    - 删除语义跟着改（重要）：删掉一条文件/文件夹消息只删聊天记录，
      共享文件夹里的那个文件/文件夹**不动**（确认框里会写明）；
      图片消息（在 _lanchat\blobs 里）还是跟着一起删
    - 老消息兼容：没有 path、只有 blob 的（v2.9 及以前发的）照常显示、打开、另存为，
